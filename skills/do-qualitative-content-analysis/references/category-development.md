# Category Development and Coding Guide

Categories differ along two independent axes: what kind of category it is, and where it sits in the system. Confusing the two produces category systems that look organized and analyze nothing.

## Types of Category

The coding process is not the same for every type. Naming the type sharpens analytic sensitivity and forces a check on whether the type suits the research question.

| Type | What it captures | Coding consequence |
|---|---|---|
| Factual | Objective or apparently objective circumstances: occupation, place, event | Assignment is largely a classification decision |
| Thematic | A topic, argument, or figure of thought, such as "environmental knowledge" | Functions as a pointer to where relevant material sits; the quality test is whether the right passages are marked, not whether segment boundaries are exact |
| Evaluative or scaling | An assessment of the material against the researcher's stated standard, with a fixed set of values such as strong / little / none | Coders apply rule-based classification to relevant passages; the value set is developed from the coded passages and settled before the final case-level coding (p. 127) |
| Analytical | A construct arrived at through sustained engagement with the data, moving beyond what thematic categories describe — for example noticing that participants keep weighing costs against benefits, and defining "cost–benefit calculation" | Cannot be assigned mechanically; requires interpretation and a memo trail |
| Theoretical | A special form of analytical category taken from or derived from existing theory, such as "cognitive dissonance reduction" | Must be tested against the material rather than confirmed by it |
| Natural | The field's own terminology, equivalent to an in vivo code — a head nurse's "tradition bearer of the unit", a student's "the eco-woman" | Keep the wording intact; the transition to an analytical category is fluid, so mark when you cross it |
| Formal | Information about the unit itself: interview length, date, word count | Metadata, not analysis |
| Ordering | Not used to code material at all; structures the category system the way headings structure a chapter | Never report an ordering category as a finding |

The eight types and their descriptions follow Section 2.2 (pp. 36–37). In the right-hand column, only the entries for thematic and evaluative categories restate the book; the others are this skill's working notes.

Coding into thematic categories is not yet the analysis: the book warns that the process must not end with coding (p. 122). The analysis happens when the coded material is examined by category, compared across cases and groups, and checked for relationships and counter-examples. Structuring QCA can do this with thematic categories alone; whether to develop analytical categories depends on the research question, so do not invent abstract categories just to look analytical.

## Structural Position

- **Main category:** broad analytic dimension linked to the research question.
- **Subcategory:** differentiation within a main category.
- **Case attribute:** contextual or descriptive property assigned to a case rather than coded repeatedly in text.
- **Theme:** the book treats “theme” and “thematic category” as synonyms (p. 39). If a project uses “theme” in another sense, define it.

Category systems in QCA are almost always hierarchical (p. 41). Position and type are separate questions (this framing is this skill's). A main category can be thematic or evaluative; a subcategory can be natural or analytical. Record both for every entry in the coding guide.

## Deductive Development

The book names these sources for deductive categories (pp. 51–52); they are not mutually exclusive, and several should be considered:

- the interview guide;
- theory guiding the study;
- the state of research, including category systems from similar studies;
- process models inherent to the object of study;
- hypotheses and assumptions;
- everyday knowledge;
- personal experience and subjective theory.

Main categories can usually be derived from the research question (p. 102). Whatever the source, process part of the data first to check that the categories and their definitions can actually be applied; 10–25% of the data is usually enough for this test (p. 103).

## Inductive Development

The book gives guidelines in six stations, some of which are passed through in cycles (pp. 66–69):

1. Determine the goal of category building from the research question.
2. Determine the category type and the level of abstraction — how close to the participants' language to stay.
3. Familiarize yourself with the data and decide the scope of the segments to be coded.
4. Read the passages sequentially, line by line, and develop categories directly on the text: assign an existing category or create a new one.
5. Systematize and organize the category system when it grows hard to oversee; group similar categories under more abstract ones.
6. Finalize the system and write the category definitions once (almost) no new categories appear — a first “saturation”. Because the remaining material is still run through before the analysis ends, fixing this point exactly is not critical (p. 68).

## Combined Development

Start with relatively few main categories (usually not more than 20) derived from the research question, the interview guide, or a reference theory, and treat them as search aids. Then develop subcategories inductively, using only the material assigned to each main category (pp. 76–77). Record which categories came from which source (this skill's addition).

## Coding Guide Template

| Field | Content |
|---|---|
| Category name | Concise label, as meaningful and precise as possible |
| Content description | What the category means, with theoretical background where applicable |
| Category application | “This category is coded if the following aspects are mentioned …” |
| Examples of applications | Quotations with reference (document; paragraph or page). A constructed example is allowed if none is typical enough, but must be marked as constructed (p. 44) |
| Other applications (optional) | “The category is also coded when …” |
| Differentiation from other categories (optional) | “The category is not coded if …; in that case category z is used” |

These six fields are the book's general scheme (Figure 2.1, p. 43). This skill suggests four more, which are not in the book: category type, structural position, a difficult case with its decision, and a version note (date, reason, recoding consequence).

Do not add a “coding unit” or “context unit” field per category. QCA does not segment the text in advance; coders mark units of meaning (pp. 45–46). State the rules for the scope of coded segments once, for the whole coding guide (p. 105): complete thoughts; several sentences or paragraphs with one meaning coded as one segment; the interviewer's question included when needed to understand the answer; a segment must still be understandable out of context.

The book distinguishes the category manual (code book: all categories and definitions, written for readers outside the project) from the coding guide: category manual + instructions for coders = coding guide (p. 44).

## Standards for a Good Category System

From pp. 41–43:

- The categories are closely related to the research questions — the most important condition.
- The categories are exhaustive. Early on, a category “other” helps capture what the developed categories miss.
- The categories are selective (distinct); depending on the application they may also be mutually exclusive.
- The categories are well formulated.
- Taken together they form a coherent whole; main categories share a similar level of abstraction.
- Subcategories are dimensions, values, or sub-aspects of their parent category.
- The categories are understandable to coders and to later readers.

Categories should be mutually distinguishable enough for the task, but they need not be logically exclusive when simultaneous coding is analytically justified.
